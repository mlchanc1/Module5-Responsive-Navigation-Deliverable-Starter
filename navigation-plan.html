2. Breakpoint evidence

Method and widths tested: I used Chrome DevTools Responsive mode and manually resized the viewport to test the navigation at multiple widths, including 320px, 628px, and 1100px.

First content failure: The navigation links began to run out of horizontal space around 628px, so this was used as evidence that the layout needed to switch to the compact menu before the content became crowded.

Chosen breakpoint in relative units: I used 64rem as the breakpoint so the navigation changes to the wide layout when enough horizontal space is available. Using rem keeps the breakpoint relative to the user's font size instead of relying on a fixed pixel value.

Long-label and zoom retest: I tested the page at 200% zoom and with the longer navigation labels. The content remained readable and usable without overlapping or being cut off, so no additional repair was needed.

5. JavaScript code defense

The navigation is initialized by adding the "js" class to the document, revealing the menu button, hiding the navigation list, and setting aria-expanded to "false". The setMenuState(isOpen) function keeps the menu's hidden state and the button's aria-expanded attribute synchronized. A click event on the menu button activates the menu and uses setMenuState() to open or close it. A keydown event listens for the Escape key, and when Escape is pressed while the menu is open, setMenuState(false) closes the menu and button.focus() returns focus to the menu button. I also used button.focus() after Escape closes the menu so keyboard focus returns to the Menu button instead of being lost.
